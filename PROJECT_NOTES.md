# Homeroom — Project Notes

Running notes on the Webster Groves Chemistry classroom site, kept up to date as work happens so a fresh session (Claude or otherwise) can get oriented quickly.

## What this project is

A React + Vite single-page app (`src/WebsterGrovesChemistry.jsx`) that renders Jay's chemistry classroom as a virtual room: a unit nav bar, a "chalkboard" area showing the current lesson's Google Slides + learning goals, and an assignments/classwork section below the fold. ## Known environment gotcha: OneDrive + git locks

The repo folder lives inside OneDrive sync (`C:\Users\Worth\OneDrive\Desktop\Homeroom`). OneDrive can hold file locks on `.git` internals (`index.lock`, `HEAD.lock`, temp objects) that block `git add`/`commit`/`push`, especially after an interrupted git operation. Symptoms: "Unable to create '.git/index.lock': File exists" or "unable to unlink" errors even though no git process is actually running.

Fix, in order of preference:
1. `Remove-Item .git\index.lock, .git\HEAD.lock -ErrorAction SilentlyContinue` from PowerShell in the repo folder, then retry.
2. If that fails (access denied), pause OneDrive sync briefly (tray icon → Settings → Pause syncing), then retry the delete.
3. Longer-term: consider moving the repo out of the OneDrive-synced folder to a plain local path to avoid this recurring.

Also: **always `git fetch`/check `git status` against origin before assuming local `main` is current** — it silently fell behind by 3 commits during this session (`git status` said "up to date" based on a stale remote-tracking ref).

Every board docked after that stops `DOCK_STEP_PX` (currently 30px) further right than the one before it, so each board's frame — and its handle — peeks out past the one in front of it instead of stacking exactly on top and burying each other. Verified this scales fine to at least ~10 panels before the fan would reach the SmartBoard's own right edge.
4. **Real aluminum frame.** Each movable panel now has an 11px flat metal-gray (`#9a9a9a`) frame on all sides (no separate darker inner groove — that read as a dark green border because it was a translucent black wash over the green board). The fixed back board stays flush/borderless, since it's meant to be the wall board everything else slides in front of, not another slab.
5. **Handles: two per board, chevron icons, direction-aware.** Every movable panel has a handle in both bottom corners (whichever side ends up exposed once a board is buried in the pile, there's always one reachable). Each handle shows `‹` when clicking it will pull the board away, `›` when clicking it will bring a docked board back — same button, direction reflects current state (`setCurrent(parked ? i : i + 1)`).
6. **Found and fixed a real click-through bug.** The handles would visually peek out from behind the SmartBoard but weren't clickable. Root cause: the SmartBoard's wrapper spans the full 60% column at z-index 1000, and doesn't visually fill that whole rectangle (padding + it vertically centers a shorter device mockup) — so the empty margin, while invisible, was still a real element sitting on top in stacking order, silently swallowing clicks meant for whatever's behind it. Fixed with `pointerEvents: "none"` on the wrapper and `"auto"` restored individually on `SmartBoard`'s three actually-visible pieces (frame, SMART label bar, marker tray) back in `WebsterGrovesChemistry.jsx`. This is the fix to remember if any *other* overlay ever needs to sit behind the SmartBoard.
7. **Per-board counters ("1/3", "2/3", ...).** Replaced the single global counter (which only ever reflected the current board) with one counter per panel, printed on its own frame next to its right handle. Hit the same category of bug as #6's cousin: the counter `<div>` had no `zIndex`, so the Face div (defined later in the DOM, also `position: absolute; inset: 0`) painted over it. Fixed by giving it `zIndex: 2100` to match the handles. The fixed back board gets the same counter too (just no handle, styled for the flush green board instead of the metal frame).
8. **Added "Testing 2"** — a second Unit 10 lesson with 5 total panels (4 movable + the fixed back board) to prove the fan-out approach holds up with more layers, not just 2.

## Session 7 — Full Agenda sliding fixes, Settings live preview rewrite (2026-08-22)

Jay reported the Full Agenda + Sliding Boards combination from Session 6 was actually broken in several ways once used for real, then separately asked for the Settings preview itself to stop being a hand-built approximation. Both threads ended up touching `ChalkboardBoardRow.jsx` and the Settings page.

1. **Full Agenda now slides as one physical board, not a bolted-on scoped slider.** Session 6 shipped Sliding Boards support under Full Agenda as a small scrolling/paginated sub-box for just the Objectives checklist — Jay's explicit correction: "The entire blackboard configuration needs to be on the whole sliding panel, like the learning goals was previously. Essentially swapping learning goals for full agenda but they should behave in the same manner." Rebuilt so Full Agenda reuses `ChalkboardBoardRow` exactly like Simple Goals does: `goalsLabel` swaps the header to "Objectives & Benchmarks," and a new `extraContent` prop carries the Essential Question/Agenda/Bell Ringer/Home Learning fields onto the same physical rail/dock mechanic. `FullAgendaBoard.jsx` was split so `useFullAgendaFields(storageKey)` (state) is called *once* in `WebsterGrovesChemistry.jsx` and handed down as props to `FullAgendaFields`/`ObjectivesChecklist` (now purely presentational) — a single source of truth whether Full Agenda is currently flat or sliding, so toggling Sliding Boards on/off never shows stale field content.
2. **Fixed a click-to-edit bug this surfaced**: after sliding a board away, clicking to edit the Essential Question (or any Full Agenda field) on the newly-revealed board silently did nothing — it would flash into edit mode and immediately revert before a teacher could type. Root cause: `extraContent` was rendered on *every* panel face, including the one docked out of sight behind the SmartBoard. Since all copies share one `editingKey`, clicking to edit flipped both the visible and hidden copies into edit mode in the same render; React then focused each new `<textarea>` in turn, and focusing the second one fired a `blur` on the first — which called `onSave` and reset `editingKey` back to `null` before any typing happened. Fixed by only rendering `extraContent` on the currently-front (`isFront`) panel — a docked panel is never visible/interactive anyway, so nothing is lost.
3. **Fixed a separate, more consequential bug**: navigating between two lessons with different panel counts (e.g. a 3-panel lesson to a 2-panel one) could leave a stale panel from the previous lesson still mounted alongside the new one — visible as two mismatched "N/total" counters at once (e.g. "1/3" and "1/2" simultaneously), with the stale one's handle unresponsive. Root cause: `buildSlidingPanels` deliberately gives every auto-split panel of one lesson the *same* `panelKey` (the lesson's own title — needed so checked-goal state stays in sync with the flat checklist), but `ChalkboardBoardRow` was also reusing that same value as the React `key` on each panel's wrapper `<div>`. Duplicate sibling keys are invalid and React silently mis-reconciles them across renders. Fixed by keeping `panelKey` for checked-state as-is but giving each panel div its own unique key (`` `${panelKey}::${i}` ``) so React always remounts cleanly. (A prior, incomplete fix earlier in the session — clamping/resetting the `current` board index on lesson change — helped a related but different symptom and is still in place; this key fix addressed the actual root cause.)
4. **Settings preview rebuilt as a real live embed, not a mockup.** Jay's ask: "can we make the setting image actually be a live preview of the page that is being changed... looks exactly like what the board looks like when the 'Back to board' button is pressed." The original preview (Session 6 follow-up) reimplemented the board's rendering a second time by hand, so it could never be fully accurate — most visibly, it had no way to show how Sliding Boards' count setting actually splits a lesson's goals, since it never ran `ChalkboardBoardRow`'s real logic at all. Replaced with `LiveBoardPreview` in `SettingsPage.jsx`: an `<iframe>` embedding the real app at `/?preview=1`, rendered at a fixed intrinsic size (1600×900, so it lays out like a real browser tab instead of reflowing at some arbitrary narrow width) and scaled down to fit via a `ResizeObserver`-driven CSS transform.
   - **Current-lesson sync**: `boardConfig.js` adds `writeCurrentView`/`readCurrentView`, a *one-way* cross-tab-synced record (real board tab writes, preview only reads) of which unit/lesson is open, keyed like every other setting. `WebsterGrovesChemistry.jsx` detects preview mode via the query param, restores that lesson on load (so the preview opens already showing what "Back to the board" would return to, not the homepage), and keeps following the real tab's navigation live via the same `storage` event mechanism `useScopedSetting` uses.
   - **Category highlight passthrough**: the old mockup drew an orange glow around whichever region (background/bulletin/layout/blackboard) matched the selected settings category. Since the preview is now a separate document, `SettingsPage.jsx` sends `{ type: "homeroom-settings-highlight", region }` into the iframe via `postMessage`; `WebsterGrovesChemistry.jsx` listens (preview mode only) and applies the same glow directly to the real board's own DOM regions.

## Session 13 — the rest of localStorage moves to Mongo too (2026-08-25)

Session 12 (#8 above) deliberately left board-formatting preferences (wall type/color, board surface, board arrangement, bulletin style, sliding boards on/off + count, which Board Content components are on, and their order) on localStorage-only, as a lower-stakes call. Jay: "i would like to have everything ultimately saving to mongo but if localstorage is needed to show instant changes then thats good too" — so this session closes that gap, the same dual-write way every other Mongo-backed field already works.

1. **New `api/boardSettings.js`** — one Mongo doc per teacherId holding an arbitrary key/value map (`{ settings: { <storageKeyName>: <value> } }`). Doesn't need to know what any individual setting means — `useScopedSetting` (see below) already treats every value as an opaque string (a preset id, `"true"`/`"false"`, a JSON-encoded array for Board Content order), so the endpoint just stores whichever key arrives. POST does a partial `$set` of `settings.<key>` only, so one teacher tweaking one dropdown doesn't round-trip (or risk clobbering) every other setting.
2. **New `src/lib/boardSettingsApi.js`** — same thin-fetch-wrapper pattern as the other `lib/*Api.js` files: `fetchBoardSettings(teacherId)`, `saveBoardSetting(teacherId, key, value)`.
3. **The Mongo sync was wired into `useScopedSetting` itself** (`boardConfig.js`), not into each of the ~10 individual settings that call it — since every board-formatting preference already flows through this one hook (`boardArrangement`, `bulletinStyle`, the five Board Content on/off toggles, `boardContentOrder`, `wallType`, `wallColor`, `boardSurface`, `slidingBoardsEnabled`, `slidingBoardsCount`), adding the sync once here is what actually made this "a storage-layer change, not a redesign" — no call site in `BoardSettingsPanel.jsx` or `WebsterGrovesChemistry.jsx` needed to change at all. `useBoardContentOrder` (built on top of `useScopedSetting`) inherits the same sync for free.
4. **How the dual-write works**: localStorage stays the first, synchronous write (unchanged) — still what a fresh page load reads before anything remote resolves, and still the only thing needed offline or with no `MONGODB_URI` configured. On mount, each `useScopedSetting` instance also fetches this teacher's remote settings map once and merges in the remote value for its own key if present (remote wins, same "last device to save wins" convention `boardContent`/`checkedGoals` already use) — gated by a `hasLoadedRemote` ref so that merge can't be clobbered by the local-write effect firing first. Every value change after that also fire-and-forgets a `saveBoardSetting` call, swallowed on failure exactly like every other Mongo write in this app.
5. **One added wrinkle over `boardContent`/`checkedGoals`**: a single page can easily mount 10+ `useScopedSetting` instances at once (Build's whole settings panel, or the real board reading all its display prefs), and each used to be fully independent — happy to each fire its own remote fetch. Added a module-level `Map` (`boardSettingsFetchCache`, keyed by teacherId) so all of them share ONE in-flight/resolved `/api/boardSettings` GET instead of 10 near-identical ones. Deliberately plain module state, not a React cache — this data isn't component-scoped, and a stale copy only matters within one page's lifetime (a full reload clears it, and the `storage` event already handles same-session cross-tab sync as before).
6. Verified: `vite build` clean; `oxlint` shows only pre-existing warning categories, nothing new. Playwright against the dev server (still no `MONGODB_URI` in the sandbox) confirmed the board still loads with no console/page errors and Board Settings' controls still write to their scoped localStorage keys exactly as before — the new Mongo calls fail silently, same graceful-degradation shape as every other Mongo feature here. **Same standing caveat as Session 12's #9**: no live Mongo round-trip tested from the sandbox (`mongodb-memory-server`'s binary download is still blocked here) — worth a real check once `MONGODB_URI` is set: change a wall color, reload, confirm it's still there; open the board on a second browser/device and confirm it matches.
7. **Net effect**: every kind of per-teacher data Homeroom saves — curriculum shape, uploaded assignments, onboarding profile, lesson board content, checked goals, and now board-formatting preferences — is Mongo-backed, with localStorage everywhere as the instant, offline-safe first write. Nothing is localStorage-only anymore.
